# Video Tools

A web application with video tools: seamless loops from uploaded videos, image-sequence-to-video assembly, speed changes, format conversion and watermarking. Deployed on Vercel: a static React frontend plus serverless functions that run ffmpeg, with Vercel Blob for file transfer (uploads and results bypass the ~4.5 MB serverless body limit).

## How it works

1. The browser uploads the file(s) **directly to Vercel Blob** via `@vercel/blob/client` (token issued by `/api/upload`; capped at 200 MB per file, video/image content types only).
2. The browser POSTs `{ tool, filename, blobUrl | blobUrls, watermarkUrl?, options }` to `/api/process`. The function downloads the blob(s) to `/tmp`, runs ffmpeg (`ffmpeg-static`, a real binary, no bash; `ffmpeg -i` doubles as the probe, so no ffprobe ships), uploads the result to Blob, and returns `{ url, downloadUrl, filename }`. The input blobs are deleted afterwards.
3. The browser downloads the result and fires a best-effort `DELETE /api/process` to remove the result blob.

A **Stop** button fades in next to the action button while a run is in flight. It aborts the whole chain client-side (upload, processing request, result download) via one `AbortController`, then deletes whatever blobs that run created; switching tabs mid-run aborts the same way. Server-side, `api/process.ts` listens for the response's `close` event and, if it fires before the response was written, kills the running ffmpeg/gifski child so the function stops encoding — best effort, since it relies on the platform propagating the client disconnect to the function.

## Formats and quality

The rule the tools are built around: **a tool hands back the format it was given.** A GIF that goes through Loop, Speed or Mark comes back a GIF, an MP4 an MP4. Changing formats is the Converter's job and nobody else's (Sequence is the other tool that asks for a format, because stills have none to keep). That keeps the tools composable: what one tool returns, the next one accepts, and a file can pass through several without changing what it is.

- **The formats** are the six in `shared/formats.ts`: MP4, WebM, MOV, GIF, WebP, AVIF. That file is the single table for both sides: the client reads it for the dropdowns and to tell whether a picked file is one the format-keeping tools can take, the functions for content types and for naming what a source is.
- **What a source is** goes by its content, not its name (`sourceFormat` in `api/_lib/source.ts`): ffmpeg's demuxer names, plus the `ftyp` brand inside the mov family (mp4 / mov / avif share a demuxer) and the codecs inside Matroska (a WebM is a Matroska file with VP8/VP9/AV1 video). A source in any other container (AVI, MKV, WMV, TS, …) **is refused** by the format-keeping tools with a pointer to the Converter — there is deliberately no fallback to MP4, since a result in a format nobody asked for is exactly the surprise the rule prevents. The client says so as soon as the file is picked, before any upload (`FormatNotice`). A file a tool *can* take is not commented on at all: the format coming back unchanged is the rule everywhere, so the UI only speaks where a file cannot go on. Animated WebP is refused everywhere: ffmpeg has no decoder for it, so it is a Converter target only.
- **One encoder per format** (`api/_lib/encode/`), used by every tool. A tool never encodes: it describes its transformation as a `Render` (ffmpeg inputs + a filtergraph ending in `[out]`) and the format's encoder appends what the format needs and runs **one** ffmpeg pass. So every result is encoded exactly once (there are no intermediate files to lose a generation to), and a GIF is made the same way — by gifski — whichever tool makes it.
- **Quality is relative to the source.** The slider is still each codec's own quality curve (x264 CRF 35→1, VP9/AV1 CRF 50→10), but with a ceiling on top: the result may spend at most `quality`% of what the source's video stream spends per second (`encode/rate.ts`; x264 `-maxrate`/`-bufsize`, VP9 and AV1 constrained quality via `-b:v`). 100% therefore means *match the source*: size follows duration and nothing else, so a reverse loop is about 2× its source, a watermarked clip about 1×. Without the ceiling CRF is absolute — CRF 1 on footage that was delivered at CRF 23 re-encodes its compression artifacts as detail, at 5–15× the size and no better than the source looked. A source in a leaner codec than the result's gets proportionally more (HEVC ×1.5, VP9 ×1.4, AV1 ×1.8 when the result is H.264), so such a result can exceed its source's size; held to the source's own rate it would come out visibly worse. Where the source's bitrate is not in ffmpeg's summary (WebM, GIF) it is measured from a packet listing, which only demuxes. Stills have no source rate, so Sequence is not capped.
  - One-pass VP9 lands well under the rate it is given (around 0.8×). A second pass would fix that at twice the time, which the 300 s limit doesn't have; accepted.
  - GIF has no rate control at all. A GIF source keeps its own dimensions and frame rate, gifski gets the slider as its quality, and a result that outgrows its source (by the frame, +10%) is encoded again at gifski 90, then 50 — the steps where gifski's size actually moves — from the PNG frames already on disk, while the function's time allows.
  - x264 under a ceiling is not bit-exact from run to run (its rate control reacts to thread timing): the same command lands within about a percent of itself.
- **What "lossless" can mean here.** Only a stream copy is truly lossless, and the tools use one wherever the whole operation allows it (below, and audio). Everything else is one encode matched to the source, which still costs one generation: at 100% an H.264 result is a touch softer than its source, not identical. Repeating tool runs repeats that.
  - **Audio** is copied, not re-encoded, whenever a tool keeps it and its codec fits the result's container (AAC in MP4/MOV, Opus/Vorbis in WebM).
  - **ffmpeg drops alpha when decoding AVIF and VP9** (it reads the colour stream only), so transparency survives GIF sources only.
  - A GIF with per-frame delays comes back with one constant delay (gifski takes a rate, not a list).
- **ffmpeg 6 vs 7** (ffmpeg-static ships 6.1.1 for Windows and 7.0.2 for Linux, so Vercel runs 7): graph changes have to be run on both (`npm run smoke -- v7 --ffmpeg <path>`). Found so far, all handled in the code and commented there: ffmpeg 7's `setpts` leaves its output without a frame rate (xfade then refuses to run, and the encoder assumes 25 fps and silently drops frames); ffmpeg 7 lists an animated AVIF as two video streams, its one-frame cover image first (so nothing may assume "the first video stream": `SourceProfile.videoIndex`, `videoPad`); the `fps` filter loses the last frame of anything that went through `overlay` (both versions), which is why format-keeping tools pass their frames to the encoders as they are (`everyFrame`).

## Tools

Each tool is a tab with its own URL (`/loop`, `/sequence`, `/speed`, `/convert`, `/mark` — TanStack Router; `/` and unknown paths redirect to `/loop`); adding a tool means one entry in `TOOLS` (client) + a handler module in `api/_lib/tools/` + its line in that folder's `TOOLS` (server), a page component under `client/src/pages/` and its line in `PAGES` (`pages/index.ts`) — routes, tabs and the SPA rewrite need no changes (the rewrite in `vercel.json` is a catch-all that already excludes `api/` and Vite's module URLs).

- **Loop**: seamless loop, in the source's format and always silent. Options: `technique` — `reverse` (plays the clip forward then reversed, no further options) or `crossfade` (adds `fadeDuration` in seconds and `startSecond` to choose the first frame, for thumbnails/social media) — and `quality` (1–100, relative to the source; see above). Each is a single ffmpeg pass. Reverse is done by the encoders (`Render.palindrome`): video appends `split → reverse → concat` after converting to the encoder's pixel format, so the buffer of reversed frames holds 1.5 bytes a pixel rather than RGBA's 4; GIF buffers nothing, gifski just reads the PNG frames a second time, backwards. Crossfade is one graph over the source opened **twice**: every piece is then a run of consecutive frames of one input in output order, so ffmpeg streams it (pieces of a single input would wait in memory for their turn — with a custom start, most of the clip). It counts in frames at the source's rate, so the pieces meet exactly. One round of the loop is *body → fade*, and `startSecond` rotates it, so it is kept between the fade-in frames and the fade-out frames. With `fadeDuration` 0 there is nothing to encode: start 0 hands the file back (video as a remux, without its audio), and another start reorders the **streams without decoding** where that is provably whole — a keyframe within 0.5 s of the start point (the loop then starts there; any further and it is encoded to the exact frame instead), cut by packet position, and the result decoded and required to show every frame of the source. Streams with B-frames (most H.264) lose a frame at such a cut and fall through to the encode; VP9 and intra-only streams come through. (The old implementation cut by timestamp and silently lost every frame up to the next keyframe.)
- **Video speed**: speed a clip up or slow it down, in the source's format. Option: `speed` slider from −3 to +3 (0 = unchanged, center). The value is a signed ratio: +1 plays 2× faster (10 s → 5 s), −1 plays 2× slower (10 s → 20 s), ±3 → 4×. No quality slider: it runs at 100%, the source's own rate. Video keeps its frame rate (speed-ups drop frames, slow-downs repeat them); a GIF keeps every frame and changes its delays instead, up to the 50 fps a GIF can show. Audio is dropped.
- **Converter**: the one tool that changes a file's format. A single "Convert to" dropdown lists the targets (MP4 / WebM / MOV / GIF / WebP / AVIF) minus the uploaded file's own format; any container ffmpeg reads works as input (AVI, MKV, WMV, …, and animated GIF/AVIF), which makes it the way in for files the other tools refuse. Video targets keep audio (copied where the codec fits, else H.264+AAC for MP4/MOV, VP9+Opus for WebM); animated-image targets (GIF/WebP/AVIF) drop it. Animated-image targets (GIF/WebP/AVIF) cap the width at 800 px. **GIF is encoded by [gifski](https://gif.ski)** (vendored binary in `api/_bin/gifski/`, ffmpeg extracts the frames): pngquant palettes + temporal dithering, far better than ffmpeg's own GIF encoder. gifski is always told the frames' own size — left to itself it silently scales anything beyond about 800×600 down — and reads them by bare name from inside their folder (the list is its command line, which Windows ends at 32k characters). GIF exposes `fps` (1–30, empty = match the source framerate) and `width` (100–800 px) next to the shared `quality` slider; a GIF is refused past 1500 frames or 384 M pixels of PNG frames (they must fit the function's `/tmp`: 600 frames at 800×800, which is what 20 s at 30 fps can come to), with a hint to shorten it, lower the FPS or the size. WebP/AVIF also match the source framerate (capped at 30). Note that GIF and animated WebP are **intra-only** formats — every frame is a standalone image with no motion compensation — so their output is often _larger_ than the source video despite smaller dimensions; they're meant for short clips where compatibility matters more than size. WebP at quality 100 switches to **true lossless** (no VP8 quantization, so no block artifacts on solid colors — expect very large files); below 100 the slider maps to libwebp 65–100, the range where VP8 keeps fine texture instead of flattening it into a visible block grid. AVIF caps at 60 s (libaom is too slow for more within the 300 s limit).
- **Mark**: stamp a watermark onto a video or an animated GIF/AVIF, which comes back in its own format. A GIF is composited in RGBA from end to end (`base: "rgba"` in `watermarkGraph`), so it keeps its transparency, its full colour resolution and its exact size; video is composited in yuv420p, which is what its encoders write. (In glass mode the lens refracts the colour of the pixels under it, so over transparent pixels it shows whatever colour the file keeps there.) Two uploads: the video and a logo image (PNG only; the client sends the logo as `watermarkUrl` next to `blobUrl`). The server enforces it too: `logoInfo` in `tools/mark.ts` goes by the codec ffmpeg probes, not the file name, so a GIF, JPEG, WebP or animated PNG is rejected with a 400 by both `/api/process` and `/api/preview`. SVG is not accepted — the bundled ffmpeg has no SVG decoder — so export the logo as PNG first. Position and size are fixed, in the bottom-right corner, and computed by one continuous formula (`watermarkLayout` in `tools/mark-graph.ts`) rather than per-shape rules. The logo is first measured by its visible pixels: a cheap extra ffmpeg pass (`alphaextract` + `bbox`) finds the alpha's bounding box and the graph crops to it, so empty canvas around a mark affects neither its size nor its place. Lengths are fractions of the frame's "unit", the geometric mean of its width and height (so landscape, portrait and square video get the same share). Size is an area budget, not a fitting box: a 1:1 logo is `sizeRatio` of the unit per side, and any other shape gets that area × elongation^`elongationGain` (elongation = long side ÷ short side, so wide and tall are treated alike and no ratio is special; gain 0 = every logo the same area, 1 = every logo the same short side, the default 0.5 gives thin, gappy logotypes some extra area over a dense square mark), split between the sides by the aspect ratio; `maxSpan` bounds either side as a fraction of the frame's matching side for banner-like logos. The gap to both frame edges is `paddingRatio` of the unit, the same for every logo (it is also the glass cell's padding). The constants live in `MARK` in `tools/mark-graph.ts`, all relative to the video so the mark reads the same at every resolution, and are meant to be tuned by eye: `api/_lib/tools/mark-graph.test.ts` (part of the client's vitest run) reads its expectations from `MARK` and runs the layout suite on the tuned values plus two quite different tunings, so it checks the model rather than pinning pixel values. Animated GIFs loop for the length of the video (`-stream_loop -1` at the demuxer, `shortest=1` in the graph). Options: `filter` (boolean, offered only for formats that can carry transparency — PNG / GIF / WebP) and `quality` (relative to the source like the other tools). Filter mode is a Liquid-Glass look: the logo's alpha becomes a thick glass lens. Its shape is turned into a heightfield (the alpha blurred at two widths — `bevelRatio` of the logo's shorter drawn side, and a third of that — remapped so it rises from 0 at the edge to full inside, averaged, and clipped to the alpha) whose Sobel gradient drives ffmpeg's `displace`: the video under the bevel is pulled in from just outside the edge (`refractRatio` of the frame's shorter side where the bevel is steepest, easing to nothing inward; displace tops out at 127 map px, 63 px of video, so the default is past that on purpose and much of the bevel bends by the full amount), with red displaced a little less and blue a little more than green (`chroma`) for a hint of dispersion. The refraction runs at 2× (displace moves whole pixels) and is brought back down. The Sobel gain never goes through `convolution`'s `rdiv`: ffmpeg-static ships different ffmpeg versions per platform (6.1.1 on Windows, 7.0.2 on Linux, so on Vercel), 6.1 ignores a given `rdiv` and 7.0 applies it, which once left the deployed glass flat while localhost bent. `rdiv` stays 1 and the gain is split between a 16-bit scale of the heightfield and integer kernel taps, which renders bit-identically on both. The flat interior is frosted (blurred by `blurRatio`, saturated, lightened with white) while the bevel keeps the refracted backdrop nearly sharp — blurred only by the floor `minBlurRatio` (1.6 px at 1080p), so small islands and thin strokes, which are bevel all the way through, don't show hard backdrop edges cutting across them, and big shapes ramp from that floor at the rim to the full frost inside; a thin rim inside the edge (1 px at 720p, scaling up), painted not white but with the refracted backdrop under it — saturated (`rimSaturation`), brightened like a colour dodge (`rimGain`) and mixed a little towards white (`rimWhite`), so it takes a vivid version of the video's hue while staying brighter than it — is lit by the slope facing the light (`lightAngle`, top-left by default) at `rimOpacity`, easing down around the shape to the `glint` level, which the rest of the rim holds all the way round (a glint that ramped up separately on the far edge notched the rim wherever an edge turned side-on to the light); an ambient gradient lies over the fill for depth on flat video (radial, centred one logo radius off the logo on the side opposite `lightAngle` and `ambientReach` radii wide, so across the logo it reads as a gently curved linear ramp: white at `ambient` opacity on that far side (bottom-right by default), fading to black at `ambientShade` of that on the light's own side, masked by the logo's alpha and under the rim); a soft shadow sits behind it; and the logo's own pixels are blended on top at `logoOpacity` (12%; a white logo brightens the glass, a dark one smokes it, a coloured one tints it). The layers are stacked on a transparent canvas and laid on the frame, so only pixels the glass or its shadow cover change, and the patch's YUV→RGB conversion and the stack's way back both name one matrix (the source's own tag as probed, which makes a JPEG frame grab or an RGB source bt601 at any size; untagged video gets bt709 from 720 lines up, bt601 below): left to auto, the way in follows the source's colour tag and the way back falls to bt601, which on bt709-tagged files (most HD exports) showed the whole patch as a faint hue-shifted box. Following the tag matters on ffmpeg 7, where filter links carry a colour space: a patch tagged differently from the frame makes `overlay` convert the whole frame, which shifted every colour of the HD preview JPEG. Everything is still one ffmpeg pass on just the patch of video under the logo (plus a margin for the blur and shadow), not the full frame; core lavfi filters only (`gblur`, `lut`, `convolution`, `displace`, `blend`, `overlay`, …), no shaders or GPU. `displace` has no sync options but always stops with its source and repeats its maps, so still logos and looped GIFs both work; the other three-way mix is done with `alphamerge` + `overlay` (which take `shortest`) rather than `maskedmerge` (which doesn't). Audio is kept, copied where its codec fits the container. Once both files are picked the UI shows an inline preview **rendered by the server with the same ffmpeg graph** (`renderWatermarkFrame` in `tools/mark.ts`, served by `/api/preview`): the browser grabs the video's first frame off its `<video>` element (downscaled to 1280 px wide — the geometry is relative, so it previews the same), posts it and the logo inline as data URLs (no Blob round trip; 8 MB cap), and gets one composited JPEG back. Whatever the graph does — blur values, future displacement maps — the preview shows it; toggling filter mode re-renders. A change mid-render aborts the request and starts over. The bare first frame stands in until the first render lands (then it's hidden, so a GIF source isn't seen playing underneath), and stays if it fails ("Preview unavailable"); on later changes the previous render stays up until the next replaces it. A GIF source is previewed through an `<img>` (a `<video>` won't decode it; a canvas draws an animated image's first frame). Other formats the browser can't decode show the frame's own note and get no preview.
- **Image sequence → video**: upload multiple images and assemble them into an animation. Options: `frameDuration` ("time per frame" in seconds, 0.02–10), output `format` (MP4 / GIF / AVIF — the one tool besides the Converter that asks, since stills have no format to keep), and `quality` (1–100 slider; the same encoders and curves as everywhere else, uncapped because stills have no bitrate to match: x264/libaom CRF, gifski quality). AVIF at quality 100 is truly lossless (RGB, no chroma subsampling — expect much larger files and slower encodes) and from 90 keeps full chroma resolution (yuv444p): encoder options only this tool asks for, because stills are pristine while a video's frames have been through both losses already. MP4 caps at CRF 1 (visually lossless) since true lossless x264 isn't playable in browsers; GIF is inherently limited to 256 colors, and gifski reads the normalized PNG frames directly. The UI shows a rough estimated output size. Frame order follows the filenames (natural sort, so `img2` comes before `img10`). Mixed sizes/formats are fine — every image is scaled and padded to the first image's dimensions (capped at 1920 px on the longest side).

## Testing

```bash
npm test      # client component tests + the api's pure helpers (vitest)
```

The unit tests never run ffmpeg. `scripts/smoke.mjs` does: it builds `api/`, pushes a set of cases (every tool, format and technique, on small synthetic inputs) through the tools' handlers exactly as `/api/process` calls them, with the Blob download faked by a file copy, and records every ffmpeg/gifski command spawned plus each result (download name, bytes, size relative to the source, probed codec / dimensions / duration). No Vercel, no Blob.

Every case also carries what has to hold for it whatever the encoders do (`expect` in `CASES`): the **format** that comes back (`"source"` for every tool but the two that are asked for one), how **large** it may be next to its source (a reverse loop ≤ 2.2×, a watermarked clip ≤ 1.15×, …), how many **frames** it has to decode to (as many as the source, or twice that for a reverse loop — counted by decoding, because a frame lost at a cut or to a frame-rate mix-up shows in neither duration nor rate), or the **rejection** a source gets that the app cannot hand back (`errorCode`). A run that breaks one lists it and exits 1. These are what caught the ffmpeg 7 differences above; run the suite on both versions before shipping a graph change.

```bash
npm run smoke -- before                 # run all cases, save under .smoke/before (gitignored)
npm run smoke -- after --diff before    # run again and compare: exits 1 if commands or results differ (or an expectation breaks)
npm run smoke -- gif --only gif,webp    # only the cases with "gif" or "webp" in their name
npm run smoke -- v7 --ffmpeg <path>     # another ffmpeg than ffmpeg-static's (Vercel runs 7.0.2, Windows installs 6.1.1)
```

A refactor should leave commands and results identical (sizes within 2%: capped x264 is not bit-exact between runs); a deliberate encoding change shows up as exactly the commands meant to change, with its effect on the sizes next to it. Outputs stay in `.smoke/<label>/runs/<case>/` to look at. `NO VIDEO STREAM` in the table means ffmpeg could not find a video stream in the result: expected for animated WebP (ffmpeg has no decoder for it), a finding anywhere else. New cases are one line in `CASES`.

The inputs are synthetic test patterns unless you supply your own: put `video.<ext>`, `animation.gif`, `logo.png` and/or `images/*` in `scripts/smoke-assets/` (gitignored; see its README) or point `--assets <dir>` somewhere else. Whatever is missing is still synthesized, and the GIF source and preview frame are derived from your video, as are the sources in the other formats (`source.mov`, `source.webm`, a small `source.avif`) and `reject.mkv`, the container the tools have to refuse. Use real footage to judge quality by eye: the outputs of every case are kept under `.smoke/<label>/runs/`.

## Deployment

```bash
vercel        # preview deploy
vercel --prod # production
```

`vercel.json` sets `api/process.ts` to `maxDuration: 300`; it sets **no memory**, so the functions get the project's default (2 GB on Hobby; check the dashboard). The reverse technique buffers all decoded frames in RAM and refuses clips whose buffer would pass `MAX_REVERSE_BYTES` (`tools/loop.ts`, 1.2 GB: what leaves the encoder its share of 2 GB) — raise the two together. `api/preview.ts` gets 60 s and the same `includeFiles` so the ffmpeg binary ships with it.

## Limits

- Uploads capped at 200 MB per file (`api/upload.ts`); very long/high-res videos can still exceed the 300 s function duration or `/tmp` space.
- The **reverse** loop holds every frame in memory (frames × width × height × 1.5 bytes), so it is refused with a 400 past 1.2 GB of them: about 13 s of 1080p at 30 fps, 3 s of 4K. A GIF is exempt (its frames are files). Crossfade streams, so it works at any length the time limit allows. Fixes: more function memory and a higher `MAX_REVERSE_BYTES`, or reversing in segments.
- Loop, Speed and Mark hand back the format they get, so they take the six formats the app writes minus animated WebP (unreadable); anything else ffmpeg reads (avi, mkv, wmv, …) goes through the Converter first, which accepts it all.
- AVIF is refused past 60 s or 648 M pixels of frames (60 s of 800×450 at 30 fps): libaom is slow, and a format-keeping tool encodes an AVIF at its own size, not the Converter's 800 px.
- Image sequences: at most 100 images per run. AVIF encoding (libaom) is slow — long sequences at high resolution can approach the 300 s function limit.
- Processing is synchronous — the browser keeps a single request open while the function works.
